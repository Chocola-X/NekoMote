## 2. “求值占 90%”的边界

7 个真实型号、正常待机及拖动/视线两种输入，共 14 组。
初轮原版 Session 测量中，`prepare_frame` 占 `advance + prepare_frame` 均值约 76%～82%。
另外以相同最终参数驱动独立 GeometryInstance，`build_frame` 比 `evaluate` 贵约数倍。
这支持优先处理几何帧构建，但不支持“任何 x86、任何真实型号都 90% 用于 Bézier”的结论。

`prepare_frame` 还包含最终节点求值和帧命令生成，不能把它全算成曲面计算；
独立 GeometryInstance 的计时也不是 Session 内嵌调用的精确拆分。
这里的会话 CPU 基准不包含 GPU、UI、声音设备线程、合成器与呈现。
原报告插桩后的 deform 时间甚至高于未插桩整帧，不能混用两套时间推导绝对比例。
没有本机函数级采样证据时，不宣称已经测出 Bézier 的独占占比或整机功耗收益。

## 3. 控制点预处理

保持世界控制点原有的 float 保存，再精确提升为 double。
Float32 UV 边界、16 个控制点的行主序累加，以及每级曲面输出的 Float32 保存均保留。
float Patch 与内部 PreparedPatch 共用同一份累加模板，不引入不同数学实现。

先试将 State 中控制点直接扩成 double：构建 P50 下降约 6.25%，
但节点求值 P50 增加约 3.35%，会话总 P50 仅下降约 2.13%。
随后将控制点放入实例固定数组，State 只借用地址，避免每个节点每次清零大块控制点。
该数组构造时一次分配，不增长、不移动，生命周期覆盖 State 借用；
observe_node 仍返回原有 float 控制点。最终不保留直接扩大的 State 实现。

本机 64 位布局的控制点存储增量约为每节点 136 字节，
本组 403～480 节点约多 54～64 KiB/GeometryInstance；Playback 中独立实例分别计费。
没有新增 GPU 资源或稳态分配。最终性能数据见验证目录汇总。

最终版与原版再交替三轮，14 组等权汇总如下（每组先取三轮中位数）：

| CPU 指标 | 均值变化 | P50 变化 | P95 变化 | P99 变化 |
| --- | --- | --- | --- | --- |
| Session advance + prepare | -5.29% | -5.59% | -4.51% | -0.73% |
| 独立 Geometry evaluate | -4.28% | -4.35% | -5.26% | -0.74% |
| 独立 Geometry build | -6.24% | -6.37% | -5.15% | -2.88% |

14 组总 P50 均下降，范围 5.20%～6.17%，总均值均下降；
但 date-a 动态组总 P99 为 605→751µs（+24.0%），Vanilla wintermaid
待机为 611→731µs（+19.6%）。其余组 P99 下降。
当前数据不能区分这些尾部变化中的调度/频率影响和实现代价；不宣称尾部无退化。
按整体均值/P50/P95 改善、两组尾部增加约 120～145µs 的权衡保留，
后续固定硬件的函数级 profile 仍应关注这两组。

## 4. 索引复用

新增字段仅为内部 C++ RenderFrame 元数据，公开 C ABI 帧布局不变。
runtime 在索引重建、触碰存储之前递增 index_revision；因此后续 mask 失败也不会
让下次成功帧借旧版本复用旧索引。每个实例继续拥有独立 producer token。

只有同 producer、非零帧/索引版本、相同索引数量且前次 prepare 成功时才省去 EBO 上传。
顶点和全部验证仍执行；新帧版本为零/无 token 时保持完整上传行为，
已有整帧 revision 早退契约不变。
prepare 失败与 reserve 会使缓存失效。另修正 GL reserve 的失效时机：
BufferData 已替换存储而 check_gl 随后报错时，旧成功 token 不能继续授权复用。

GL/GLES 的动态对照为同一个冻结二进制，唯一变量为是否将 index_revision 置零。
每组 600 帧，原先均上传 600 次，现在为 16 或 26 次；
索引字节减少约 97%，顶点上传字节相同。每个新版本仍完整验证所有索引。
三轮每组指标先取中位数，再对六组变化率等权汇总：

| 指标 | GL | GLES | Vulkan |
| --- | --- | --- | --- |
| prepare P50 | -19.19% | -19.83% | -12.06% |
| 会话 + prepare/render/submit CPU P50 | -1.87% | -2.04% | -0.69% |
| 等本帧 GPU 完成的端到端 P50 | -3.64% | -3.17% | -0.52% |
| 端到端均值 | -2.98% | -3.61% | +0.43% |
| 端到端 P95 | -3.80% | -2.34% | +2.07% |

这些是本机 1280×720 离屏串行完成的测试，不包含桌面 swap/present 或真实合成器。
尾部噪声较大，CPU P99 个别组仍上升，不能声称所有分位数改善。
Vulkan 的 memcpy/prepare 减少约 4～5µs，但等 GPU 完成的延迟没有稳定总体改善：
wintermaid 待机组端到端均值 +6.89%、P95 +15.52%，其他五组均值下降。
这项在 Vulkan 的确定收益是 CPU 准备与拷贝量，不是 GPU 渲染或功耗。
结合 GL/GLES 的稳定收益及用户允许局部代价的标准保留；明确记录上述局部回退，
不把不同链路收益直接相加，也不宣称 Vulkan 端到端已经提速。

## 5. 高风险求值优化建议

值得继续研究，但先做独立候选，不把报告的 2.5～4 倍、60%～75% 估算当验收承诺。

1. 先补真实模型的函数级 profile，区分曲面计算、链遍历、节点求值和驱动提交；
   覆盖待机、拖动、嵌套曲面、物理、遮罩和不同 FPS，而非只用最坏合成网格。
2. 优先尝试不重排每个点累加的独立点/独立坐标向量化和已证明输入相同的复用。
   SIMD 本身不必改变数学结果，但必须逐点保留顺序、Float32 边界，禁止隐式 FMA/
   fast-math，并验证编译器、x86/ARM 的实际产物。不能按原网格行列假定后续 UV 相同。
3. 两趟张量收缩会改变结合顺序。保留原实现作为冻结对照和原 WebGL 的独立真值，
   记录完整几何/UV/颜色/拓扑、误差分布及遮罩边缘画面，再决定是否满足既有门槛。
   不通过时撤回候选；不能重生成 golden 或放宽门槛把差异变成“通过”。
4. 每次只接受一个候选，先精确性，再 Release 的 CPU/P50/P95/P99、上传量、
   内存/显存及真实呈现测量。公式变化若需要接受画面误差，是另一个明确任务，
   本轮“允许局部性能回退”的授权不等于允许正确性下降。
