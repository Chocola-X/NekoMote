# player 切换模型后的显存、内存调查

调查基线 `bc2a386550ec6c02d655025d0ba40a1d170f4f1a`，Codex / GPT-6
（精确变体未知）。用户观察到 Chocola 多次换装后显存可升至 133 MB，
重启同一模型约 71 MB；切换其他服装又可能回落，并非持续无界增长。

本机复现了 OpenGL 的历史相关显存上涨。返回同一模型后，程序拥有的纹理和缓冲区
数量、容量与冷启动一致，旧模型已经销毁；单次 GPU 完成等待能回收大部分额外显存。
CPU 侧同时存在 glibc 已释放空闲页的保留。证据支持驱动延迟回收/内部存储复用和
分配器保留页，不能把监控数字上涨直接解释成旧模型泄漏。
Vulkan 本轮也有 RSS 上涨，但相同序列返回目标后的显存恢复了原值；不能据此否定
用户在其他切换序列中的 Vulkan 观察，也不能将 GL 的具体归因直接套给 Vulkan。

## 测量条件

- Xeon E5-1680 v4、RTX 3080 Ti 12 GiB、NVIDIA 580.82.09；
  Manjaro Linux 6.6.107、glibc 2.42、KDE/X11，GLFW 实际平台为 X11。
- Release/O3/LTO/Werror。OpenGL 3.3/EGL，普通窗口的 swap interval 1；
  Vulkan 使用普通窗口的同步呈现路径。
- 正常可见窗口，1920×1080、目标 60 FPS，有声音、共享 UI、背景 `BG_22A`。
  不使用 `--capture`、`--measure-frames`、`--check-window`、隐藏窗口或截图读回。
  诊断记录确认窗口 `visible=1`、`iconified=0`、framebuffer 为 1920×1080。
- 使用 `experiments/NekoMoteAssets/assets/` 的压缩 PNG、`model.nkm` 和 FLAC；
  私有配置放在 evidence 目录，`--no-save`，未改写用户资产配置或桌面设置。
- 先以原版 player 测冷启动。诊断版仅在正常帧循环中添加自己的 Controller 命令入口、
  资源计数及低频记录；经应用自己的 `request_switch_character` 走原有异步加载、
  GPU 准备、提交、渐变和释放路径，没有系统键鼠注入。
- 两种后端分别按目录序遍历其余 35 个 Chocola 型号，最终切回
  `chocola/casual-a-no-bell`，共 36 次切换，每次间隔约 5 秒。
  最后保持约 30 秒，再分别做单次完成等待、单次 `malloc_trim(0)` 归因实验。
  GPU 采样串行，NVML 和 `/proc` 每秒取样，PSS 每 5 秒取样。

以下单位均为 MiB，阶段值取末尾稳定样本中位数；切换瞬间的新旧模型共同驻留不计入
返回目标后的稳态。NVML 记录的是进程显存，不使用整个桌面的 GPU 使用率推断本程序开销。

## OpenGL

原版 player 首次冷启动：RSS **147.8**，显存 **71.3**，与用户的重启基线接近。
末尾再用完全相同原版二进制和参数启动，RSS 为 **218.0**，显存仍为 **71.3**。

| 带 API 计数的同一进程 | RSS | 显存 |
| --- | ---: | ---: |
| 目标模型冷启动 | 250.0 | 71.3 |
| 36 次切换后返回目标，等待约 30 秒 | 291.2 | 105.3 |
| 单次 `glFinish` 后 | 283.2 | 75.3 |
| 再单次 `malloc_trim(0)` 后 | 246.8 | 75.3 |

不同进程的驱动库驻留存在较大波动：重复原版与诊断进程均观察到 Mesa/LLVM 映射，
原版复测中 LLVM 的 RSS 达 82.46，Gallium 为 10.25；拦截版重复冷启动 RSS 为 223.0。
这部分加载的具体触发点尚未定位，不能将跨进程的绝对 RSS 差直接当作代码回归，
也不能断言是 API 拦截引起。上表仅比较同一诊断进程内的阶段变化，并另外运行没有
API 拦截的控制版核查。显存冷启动与原版均为 71.3。

无 API 拦截的控制版按 7 套服装重复两轮，再返回目标，共 15 次切换，
显存仍从 **71.3 增至 109.3**；单次完成等待后降至 **85.3**。
因此显存现象并非 API 计数拦截造成。该控制版 RSS 从 278.5 增至 309.7，完成等待后
为 297.7，再次 trim 后为 271.9；其绝对值同样不能替代原版基线。
控制版普通循环的稳定采样约 59.6 FPS，单次 `glFinish` 耗时
约 **7.86 ms**；这是一次调用的耗时，尚不等于完整的切换帧尾延迟测量。

冷启动和返回目标后，记录完全相同：

- 6 张存活纹理，名义存储 **48,701,440 bytes（46.45 MiB）**。
- 6 个缓冲区，共 **274,344 bytes**；2 个 FBO、3 个 VAO、8 个 program。
- Controller 为 Idle，旧 CPU program/instance 和旧 GPU renderer 均已释放。
- 纹理累计申请 1,325,358,468 bytes、累计删除/替换 1,276,657,028 bytes，
  差值正好等于当前存活纹理容量。不是遍历过的模型图集一直挂在 renderer 上。

相同对象集合下，单次 `glFinish` 使 NVML 显存减少 **30 MiB**，RSS 减少 **8 MiB**。
因此，这部分增量与驱动的提交完成/存储回收时机有关；仅凭这些数据不能进一步确定
是哪个内部池、孤立缓冲区 backing 或哪类驱动分配。不能把 GL 删除调用已经返回，
理解成监控数字必须立即恢复到冷启动值，也不能泛化成 Linux 内核漏回收显存。

堆存活块从约 44.92 增至 45.67，空闲块从约 8.66 增至 52.40。
`malloc_trim` 后 RSS 再下降 **36.4 MiB**，而模型资源不变，支持分配器保留空闲页的归因。
释放 C++ 对象和把空闲页交还内核是两个不同阶段。

## Vulkan

原版 player 冷启动：RSS **172.2**，显存 **64.5**。
API 计数版冷启动 RSS **176.7**、显存 **64.5**；36 次切换后返回目标，
RSS **196.2**，显存仍为 **64.5**。
单次 `vkDeviceWaitIdle` 未改变上述两项数值；随后单次 `malloc_trim(0)`
使 RSS 降至 **178.2**，显存仍为 **64.5**。

冷启动和返回目标的显式 `VkDeviceMemory` 均为 **14 块、60,633,928 bytes**。
返回时累计分配 2,345,256,032 bytes、释放 2,284,622,104 bytes，差值与存活量吻合。
这些计数包含应用申请的 host/device memory，不包含驱动内部存储和 swapchain
隐式分配，不能直接当作“物理显存占用”。

Vulkan player 在帧开始已经等待前次提交，旧 renderer 的销毁也遵循该边界；
代码没有照搬 GL 的异步销毁假设。当前有限序列未复现用户所述 Vulkan 返回目标后
显存长期翻倍，因此该项保留为未复现，而非宣布所有 Vulkan 切换情况无问题。

## 代码生命周期核查与优化方向

`apps/player/main.cpp` 的候选 renderer 在加载时独立创建；提交后只保留一个旧
renderer 用于渐变，Controller 渐变结束先销毁旧 instance 再销毁 program，
player 随后销毁旧 renderer。未变化的背景转移所有权继续使用。
GL renderer/Intermediate 析构删除图集、缓冲区、FBO 和纹理；
VK renderer 释放 pipeline、descriptor、image/buffer 及对应 memory。
本次稳定样本的资源计数与这些释放路径一致。

可以继续优化，但应按收益和副作用分别验收：

1. **降低切换期间的资源创建/销毁。** 分离模型资源与同设备的 shader、固定尺寸
   composition/mask 目标，跨换装复用合适的对象，避免每套服装重建全部 renderer。
   需要保留渐变所需的两个模型及失败事务，不能靠提前释放当前模型破坏切换。
   复用池必须有界；一直保留最大图集反而可能抬高稳态显存。
2. **只在切换完成的边界评估回收。** 单次 `glFinish` 已证明可释放约 30 MiB，
   但它会阻塞 CPU 等 GPU，不能加入每帧路径。需要单独测量切换卡顿、呈现和尾延迟，
   并比较 fence/延迟清理方案，才能决定是否采用。GL 的结果不构成给 VK 再加等待的理由。
3. **减少加载临时堆与分配器滞留。** 继续优先用可直接释放的临时映射和清晰所有权。
   `malloc_trim` 在本机能回收空闲页，但它作用于整个进程，在 Qt 插件里还会影响宿主；
   不能不加边界地塞入公共库或每帧调用。若采用，应限定宿主和显式加载结束/空闲时机，
   再验证后续切换的缺页、CPU 与延迟。

本轮仅完成调查与归因，没有将强制同步、进程级 allocator 调参或定时 trim 加入产品。
后续已落实 GL program/VK pipeline 的固定资源复用，见[实现与对照测量](renderer-resource-sharing-2026-10-19.md)。
该轮减少了重复创建，但未测得稳态显存下降；本报告中的原始基线结论仍独立保留。
PNG 极限压缩改变磁盘字节，解码后的图集像素与容量未变；本次额外显存不能用 PNG
压缩率解释。这里也没有做 CPU/GPU 提速、功耗或长时间运行的认证。

## 证据与范围

原始证据位于 ignored `build/evidence/player-switch-memory-20261019/`，包含原版与
诊断二进制 hash、完整命令和型号序列、逐秒内外部记录、日志、smaps、诊断源码与构建脚本。
汇总见 [机器记录](validation/player-switch-memory-2026-10-19.json)。
七次可见窗口运行均完成：原版/冷启动对照采样约 18 秒后由启动器结束，完整切换诊断
通过自己的关闭命令退出，返回码均为 0。两组 36 次切换的稳定末尾均确认旧资源已释放，
用户配置 hash 不变。本轮正式变更仅为调查文档和记录，未重复运行不受影响的 CTest。

有限次切换不能证明不存在所有泄漏；本轮确认的是本机这组普通可见 player 条件下的
资源生命周期与可回收增量。未验证其他驱动、Plasma 嵌入宿主、多屏、resize、全部角色
混合序列或数小时运行。不将旧隐藏窗口、30 FPS、静音基准混入这里的比较。
